# Бизнес-логика ZETOM CRM 

**Цель документа:** Согласование архитектуры работы с заявками, системы уведомлений и разграничения ответственности (Ролевая модель).

---

## 1. Жизненный цикл заявки (Lifecycle)

Процесс контроля в системе разделен на два независимых уровня. Это позволяет четко разделять глобальную «актуальность» клиента и текущую оперативную стадию работы.

### 1.1. Глобальные статусы (Актуальность)
Определяют, находится ли клиент в работе в принципе:
* **Active (Активная):** Заявка находится в обработке (на любом из четырех циклов).
* **Archive (Архивная):** Работа завершена или принудительно остановлена. Данные «заморожены» для истории и аналитики.

### 1.2. Операционные циклы и их статусы
Каждый этап (цикл) — это отдельная рабочая область с документами. Внутри текущего цикла заявка проходит через следующие состояния:
* **New (Новая):** Этап только начат, активных действий еще не было.
* **In Progress (В процессе):** Специалист начал редактирование данных или внес новую информацию.
* **Waiting (Ожидание):** Система зафиксировала отправку Email клиенту и ожидает обратной связи.
* **Done (Готово):** Работа по текущему циклу/документу полностью завершена.

## 2. Цикл NULL: Санитарный шлюз и защита данных

**NULL** - это первичный буфер для всех входящих обращений с сайта. 

**Для чего это в системе:**
1. **Фильтрация мусора:** Специалист отсеивает спам и «пустые» запросы до того, как они попадут в основной операционный отдел (Oferta).
2. **Контроль дубликатов:** Система в фоновом режиме проверяет Телефон, Email и ИНН. К моменту открытия заявки сотрудник уже видит вердикт: «Чисто» или «Найден дубликат» (с указанием ссылки на оригинал).

## 3. Ролевая модель: Разграничение ответственности

### 3.1. Иерархия доступа
Система построена на строгом подчинении: 
**Директор (Admin) > Глава отдела (Department Head) > Специалист (Specialist)**

### 3.2. Специальные роли
Эти роли находятся вне основной иерархии и решают специфические задачи:
* **Кастомный пользователь:** Роль с динамическими правами (настраивается под задачу). Не может быть выше Админа, но может быть наделена равными правами (например, для заместителя).
* **Аудитор:** Техническая роль для разработчика. **Без права правки** каких-либо данных. Только просмотр логов и инцидентов для контроля корректности работы системы.

### 3.3. Таблица полномочий
| Роль | Бизнес-смысл | Уровни доступа |
| :--- | :--- | :--- |
| **Директор (Admin)** | Владелец системы | Максимальный доступ. Управление всеми заявками, логами и учетными записями. |
| **Кастомный пользователь** | Доверенное лицо | Гибко настраиваемая роль «выше обычного» для решения управленческих задач. |
| **Глава отдела** | Диспетчер / Контролер | Видит заявки своего отдела. Назначает ответственных. Контролирует сроки. |
| **Специалист** | Исполнитель | Видит только те заявки, на которые назначен лично главой отдела или админом. |
| **Аудитор** | Техконтроль | Режим «Read-only» (только чтение) для технического аудита системы. |

## 4. Система уведомлений и контроля (Вопросы для согласования)

Для настройки эффективной коммуникации нам нужно определить триггеры оповещений:

1. **Первичное назначение:**
   - Заявка падает в NULL → Уведомление Главе отдела для распределения.
   - Глава отдела назначает Специалиста → Уведомление Специалисту.
   
2. **Контроль изменений:**
   - Нужно ли уведомлять Вас или Главу отдела о каждом промежуточном изменении (статус `In Progress`)? 
   - Или достаточно оповещения только по фактическому завершению ключевых этапов (статус `Done` в конце цикла)?

3. **Критическое информирование:**
   - Нужно ли мгновенное уведомление руководству (Директору или кастомному пользователю), если заявка принудительно переводится в статус **Archive**?
