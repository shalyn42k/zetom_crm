# Деплой ветки `feat/step-notes-unification` — runbook

> **Это инструкция для агента, выполняющего деплой на боевом сервере.**
> Читай целиком до первой команды. Здесь есть шаг, который нельзя выполнить
> задним числом: счётчик строк снимается ДО миграции, потому что миграция
> удаляет таблицу, из которой он считается.

**Дата подготовки:** 2026-08-25
**Ветка:** `feat/step-notes-unification` (29 коммитов, 605 тестов зелёные локально)
**Спек:** `docs/superpowers/specs/2026-08-24-step-notes-unification-design.md`

---

## 1. Что этот деплой делает с данными

Модель `clients.ClientInteraction` (история контактов с клиентом) сливается в
`zetom.StepNote`. Три миграции:

| Миграция | Действие | Обратимость |
|---|---|---|
| `zetom.0018_document_chain` | добавляет два nullable FK | обратима |
| `clients.0010_migrate_interactions_to_step_notes` | **копирует** все строки `ClientInteraction` в `StepNote` | реверс — `RunPython.noop`, откат НЕ удаляет копии |
| `clients.0011_delete_clientinteraction` | **удаляет таблицу** `clients_clientinteraction` | данные не восстанавливаются |

Вместе это означает: **после деплоя вернуть исходные данные можно только из
дампа.** Отката миграциями не существует.

## 2. Как миграции запускаются

Автоматически, без отдельной команды. `docker/entrypoint.sh:11` выполняет
`python manage.py migrate --noinput` при старте контейнера `web`. То есть
обычный `./deploy.sh` уже применит всё перечисленное выше.

Контейнер `scheduler` миграции не запускает — у него `SKIP_DJANGO_INIT=1`.

## 3. Порядок действий

### Шаг 1. Снять дамп и зафиксировать счётчик — ОБЯЗАТЕЛЬНО

Выполняется до любых `git pull` и `deploy.sh`.

```bash
cd <корень проекта на сервере>
set -a; . ./.env; set +a          # подтянуть DB_NAME / DB_USER

# Полный дамп
docker exec zetom-db pg_dump -U "$DB_USER" "$DB_NAME" \
  > "backup-pre-stepnotes-$(date +%F-%H%M).sql"

# Счётчик ДО. Запиши число — после миграции этой таблицы уже не будет.
docker exec zetom-db psql -U "$DB_USER" -d "$DB_NAME" -tAc \
  "SELECT count(*) FROM clients_clientinteraction;"
```

Проверь, что дамп непустой (`ls -lh backup-pre-stepnotes-*.sql`) и что счётчик
получен. **Если дамп не снялся или счётчик не получен — остановись, дальше не иди.**

### Шаг 2. Переключиться на ветку и задеплоить

```bash
git fetch origin
git checkout feat/step-notes-unification
git pull
./deploy.sh
```

`deploy.sh` пересоберёт образ и перезапустит контейнеры; миграции применятся
при старте `web`.

### Шаг 3. Убедиться, что миграции прошли

```bash
docker logs zetom-web 2>&1 | grep -E "Applying|Traceback|Error" | tail -20
docker exec zetom-web python manage.py showmigrations clients zetom | grep "\[ \]"
```

Второй запрос должен вернуть пусто (все применены). Если в логах есть
`Traceback` — переходи к разделу «Откат».

### Шаг 4. Сверить данные — ОБЯЗАТЕЛЬНО

```bash
docker exec zetom-db psql -U "$DB_USER" -d "$DB_NAME" -tAc \
  "SELECT count(*) FROM zetom_stepnote WHERE kind='contact' AND person_id IS NOT NULL;"
```

Это число должно **совпасть** со счётчиком из Шага 1.

**Про `person_id IS NOT NULL`:** квалификатор обязателен. Более ранняя миграция
`zetom.0016` уже пометила все старые `StepNote` как `kind='contact'`, но у них
`person_id` пуст. Без этого условия счёт будет завышен, и покажется, что
данные размножились.

**Если числа не совпали — немедленно откат (следующий раздел).** Не пытайся
доразбираться на живой базе.

### Шаг 5. Проверить работоспособность

```bash
docker exec zetom-web python manage.py check --deploy 2>&1 | tail -5
docker ps --filter name=zetom --format "{{.Names}}\t{{.Status}}"
```

Все четыре контейнера (`zetom-db`, `zetom-web`, `zetom-scheduler`,
`zetom-cloudflared`) должны быть `Up`.

Затем в браузере, залогинившись:

- карточка персоны и карточка фирмы — панели «Zaplanowane» и «Historia kontaktów»;
- кнопка «Dodaj kontakt» → в модалке переключатель «Kontakt» / «Przypomnienie»;
- карточка заявки — кнопка «Dziennik kontaktów», общая лента заявки и её документов;
- карточка оферты — кнопка создания злецения; после создания оферта уходит в `done`.

## 4. Откат

Миграциями откатиться нельзя. Только восстановление из дампа Шага 1.

```bash
# 1. Остановить приложение, чтобы оно не писало в базу
docker compose -f docker-compose.prod.yml stop web scheduler

# 2. Восстановить
docker exec -i zetom-db psql -U "$DB_USER" -d postgres -c \
  "DROP DATABASE \"$DB_NAME\";"
docker exec -i zetom-db psql -U "$DB_USER" -d postgres -c \
  "CREATE DATABASE \"$DB_NAME\" OWNER \"$DB_USER\";"
docker exec -i zetom-db psql -U "$DB_USER" -d "$DB_NAME" \
  < backup-pre-stepnotes-<твой файл>.sql

# 3. Вернуть код на предыдущую ветку
git checkout <ветка, которая была до деплоя>
./deploy.sh
```

Перед `DROP DATABASE` ещё раз проверь, что файл дампа на месте и непустой.

## 5. Чего делать НЕЛЬЗЯ

- **Не редактировать и не удалять миграции** `clients/0004`, `clients/0010`,
  `clients/0011`, `zetom/0016`, `zetom/0017`. Они применены; переписывание
  истории миграций ломает базу.
- **Не запускать `migrate clients 0009`** в попытке «откатиться». Реверс `0010` —
  `noop`, поэтому повторный прогон вперёд **продублирует все строки**: ничто не
  накладывает уникальность на `StepNote`.
- **Не запускать `makemessages`** на сервере. Каталоги переведены и
  скомпилированы; `entrypoint.sh` сам выполняет `compilemessages`.
- **Не пропускать Шаг 1 и Шаг 4.** Это единственные две точки, где ошибка
  миграции ловится до того, как станет необратимой.

## 6. Известные ограничения этого релиза

Не дефекты, но знать стоит:

- `LANGUAGE_CODE` в настройках — `en`. Польские переводы в каталоге есть и
  скомпилированы, но интерфейс отдаётся на английском, пока значение не
  сменят на `pl`.
- Напоминание, поставленное с карточки документа, не привязано к персоне —
  оно видно и закрывается на карточке документа, но не появляется в панели
  «Zaplanowane» карточки персоны. Так задумано: у такого напоминания нет
  собеседника.
- Модалка на карточке документа отказывается сохранить контакт с пустой датой
  разговора, тогда как со стороны карточки клиента подставляется текущая.
  Расхождение UX, данные не страдают.
