# Как работать с создание фич и новых модулей в проекте

## По веткам

В проекте используется такая система веток(**вместе с их иерархией**):
1. **`main`** — Стабильный код. Сюда пушу только Я, когда проверю весь код и он будет всем правилам поддерживаться.
2. **`test`** — Веткат для последней проверки всего, перед тем как мерджить с веткой **`main`**.
2. **`develop`** — Ветка для тестирования, проверки и нахождения багов, и всего дерьма.
4. **`feature/название_модуля`** — Ваша рабочая ветка для конкретной задачи.

---

### Как начать работу с ветками

Если вы начали работать над новым модулем в проекте, вы обязаны соблюдать эти правила чтобы у вас все работало:

1. Для начала вы выбираете ветку в зависимости от того с каким модулем вы будете работать, если ваш модуль не прошел все этапы проверки а именно **`develop>test>main`**, и сейчас не находится в ветке **`main`**, то вам стоит выбрать ветку в соотвествии с той с каким модулем вы будете работать.

В итоге после выбора ветки, в ней вы производите:
   ```bash
   git checkout -b feature/название_ветки_которую_вы_до_этого_создали
   ```
2. Если у вас что-то сломалось, код не работает либо что-то еще после пункта 1.
То вы решаете это сами, если это причина чисто ваша локальная - фиксите.
Если вы нашли ошибку в коде который находится в ветке **`main`** - сообщаете.

3. После того как вы закончите работу над модулем/фичей и **ОБЯЗАТЕЛЬНО КТО-ТО УЖЕ СДЕЛАЛ MERGE ВАШЕЙ ВЕТКИ В ДРУГУЮ И ОН ПРОШЕЛ УСПЕШНО**, вы обязаны удалить свою ветку чтобы не мусорить ветками в проекте. Команды для удаления:

* Команда для удаления локально:
   ```bash
   git branch -d название_ветки
   ```
> Если не проходит то хуярьте **`--force`** (в конце команды)

* Команда для удаления на гите для всех(идет второй):
   ```bash
   git push origin --delete название_ветки_которую_вы_удалили_локально
   ```

---

### Внедрение новых фич

Когда вы закончили че-то делать, то чтобы внедрить правльно и все не сломать вашу ветку нужно соблюдать такой порядок.

1. Во время того как вы пишите код модуля стоит создать файл md формата в папке **zetom_crm/DOCS/**, назваз его название_вашего_модуля+ваше_имя, пример - **`iso_login_tymur.md`**.
2. К ветке желательно чтобы вы прилагали:
* Логику работы модуля(в текстовом виде).
* Диаграму которую вы сохраняете так же в **`zetom_crm/DOCS/DIAGRAMS`**(если логика сложная). 
> Так же вы все это дублируите челу по тестам когда закончили в лс.
3. Как это все слить в ветку develop:
   ```bash
   git push origin название_вашей_ветки
   ```
   Затем зайти на гитхаб и открыть pull request для ветки develop из вашей, и запулить если нет никаких конфликтов.

> Молиться

### Доп команды для пользованием гитом
1. Показывает изменения которые ты делал, где, когда и для чего.
   ```bash
   git status
   ```
2. Показывает все коммиты в нынешней ветке.
   ```bash
   git log
   ```
3. Подгатавливает либо один/несколько, либо все файлы к отправке на гит.
   ```bash
   git add . [либо имя файла]
   ```
4. Сохраняет твои изменения локально, **ПОЖАЛУЙСТА ПИШИТЕ ВСЕ ЧТО ВЫ ДЕЛАЛИ В ЭТОМ КОММИТЕ В СКОБОЧКАХ ЧТОБЫ ВАМ И МНЕ БЫЛО ЯСНО**.
   ```bash
   git commit -m "ваш понятный прекрасный текст"
   ```
5. Команда для отправки всего этого чуда на гит.
   ```bash
   git push origin название_ветки
   ```
6. Синхронизирует свежие изменения с гита с вашим кодом.
   ```bash
   git pull origin название_ветки
   ```
7. Если вы комитите в ветку где были комиты от других контрибуторов либо от вас самих но через сайт, то для начал вам стоит прописать эту команду а затем пушить ваш код.
   ```bash
   git pull --rebase origin имя_ветки_в_которую_вы_хотите_запушить
   ```

## Маркировка AI-кода

Весь код, написанный или существенно отредактированный ИИ (ChatGPT, Claude, Codex и т.п.), **обязан** быть помечен комментарием. Это нужно чтобы:
- при дебаге в проде сразу видеть, где код «чужой» и к нему нужна двойная проверка;
- через grep быстро находить все AI-места (`grep -rn "AI-generated\|AI-edited" .`);
- знать, какой моделью и когда писалось — модели меняются, их стиль и баги тоже.

### Формат

Python:
```python
# AI-generated (<модель>, <YYYY-MM-DD>): короткое описание
# AI-edited (<модель>, <YYYY-MM-DD>): что именно изменено
```

HTML / Django-шаблоны:
```html
<!-- AI-generated (<модель>, <YYYY-MM-DD>): короткое описание -->
{# AI-generated (<модель>, <YYYY-MM-DD>): короткое описание #}
```

Поле `<модель>` — например `claude-opus-4-7`, `gpt-5`, `codex`. Если не помнишь/не знаешь — пиши `unknown, legacy`.

### Куда ставить

- **Весь файл писал ИИ** → маркер первой строкой (под `{% extends %}` / shebang / module docstring).
- **ИИ писал одну функцию/класс/блок** → маркер строкой выше `def`/`class`/`@decorator`.
- **ИИ правил существующий код** → используй `AI-edited`, а не `AI-generated`.

### Когда маркер снимать

Если ты переписал AI-код вручную **больше чем на 50%** — убери маркер. После этого код считается твоим, и ты за него отвечаешь.

### Что НЕ помечать

- Автогенерённое Django (миграции, `startproject`, `startapp`) — это не ИИ.
- Сниппеты, скопированные со Stack Overflow или из документации — это не ИИ.
- Код, где ты спросил у ИИ «как сделать X», а потом **сам** написал реализацию с нуля.

### Пример

```python
# AI-edited (claude-opus-4-7, 2026-04-21): simplified to render static design mockup only
@action(description="Request Info", icon="article", url_path="request-info")
def request_info_action(self, request, object_id):
    return render(request, "admin/zetom/requestmain/request_info.html", ...)
```
