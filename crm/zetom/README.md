## 1. Функциональное назначение

Основной модуль CRM. Обрабатывает весь жизненный цикл заявки — от момента её поступления от клиента до перехода в цикл `Oferta`. Включает публичную форму приёма заявок, логику валидации, продвижения по циклам и отображение в панели администратора.

**Текущий охват циклов:**
| Цикл | Статус |
| :--- | :--- |
| `null` → `RequestMain` | Реализован |
| `RequestMain` → `Oferta` | Частично реализован (создаётся запись, цена = 0) |
| `Oferta` → `Zlecenie` | Заглушка (не реализован) |
| `Zlecenie` → `Wniosek` | Не реализован |

## 2. Алгоритм работы (Логика)

### Цикл 1: Приём заявки (null → RequestMain)

1. Клиент заполняет публичную форму на странице `GET /zetom/email/`.
2. `POST /zetom/email/` — данные валидируются через `AddRequestFormNull` (польский NIP, формат телефона).
3. При успехе создаётся запись `RequestNull` в БД.
4. Автоматически уходит email-уведомление сотруднику через `send_notification_to_staff()`.
   - Если отправка email упала — запись в БД **сохраняется**, ошибка перехватывается.
5. Сотрудник открывает `RequestNull` в Django Admin.
6. Нажимает кнопку **Approve** (detail-action).
7. `approve_null_action()`:
   - Создаёт или обновляет `RequestMain` с данными из `RequestNull` (через `update_or_create` по `from_null`).
   - Soft-удаляет `RequestNull` (запись уходит в архив, не стирается физически).
8. Сотруднику уходит email `send_notification_approve_null()`.
9. Автоматический редирект на страницу созданного `RequestMain`.

### Цикл 2: Переход к Oferta (RequestMain → Oferta)

1. Сотрудник открывает `RequestMain` в Django Admin.
2. Нажимает кнопку **Oferta** (detail-action).
3. `approve_oferta_action()`:
   - Создаёт или обновляет `Oferta` с данными из `RequestMain` (через `update_or_create` по `from_main`).
   - При первичном создании выставляет `price = 0` — сотрудник должен вручную указать цену.
4. Автоматический редирект на страницу созданной `Oferta`.
5. Сотрудник вручную дозаполняет `Oferta` (цена и прочие поля).

> **Важно:** Поле `from_main` в `Oferta` — read-only в админке. Оно проставляется только программно через action и не доступно для ручного редактирования.

### Цикл 3: Zlecenie (заглушка)

Кнопка **Zlecenie** в `RequestMainAdmin` существует, но выводит сообщение `"no zlecenie :("` и ничего не делает. Реализация в планах.

## 4. Изменения в базе данных

Все таблицы создаются миграцией `zetom/migrations/0001_initial.py` (от 2026-04-16).

Все модели наследуют `SafeDeleteModel` — физического удаления строк нет, записи помечаются флагом `deleted`.

| Таблица | Ключевые поля | Связи |
| :--- | :--- | :--- |
| `zetom_requestnull` | `phone`, `email`, `company_nip`, `company_name`, `created_at` | — |
| `zetom_requestmain` | `phone`, `email`, `company_nip`, `company_name`, `full_name`, `address`, `notes`, `created_at` | `from_null` → `RequestNull` (OneToOne, SET_NULL) |
| `zetom_oferta` | `phone`, `email`, `company_nip`, `company_name`, `price`, `created_at` | `from_main` → `RequestMain` (FK, CASCADE) |

**Абстрактная база `RequestTemplate`** содержит общие поля (`phone`, `email`, `company_name`, `company_nip`) и не создаёт отдельной таблицы.

**Валидация полей:**
- `phone` — `PhoneNumberField`, регион PL по умолчанию (настройка `PHONENUMBER_DEFAULT_REGION` в settings).
- `company_nip` — regex `^\d{10}$` на уровне модели + `PLNIPField` на уровне формы (двойная проверка).
- `email` — стандартный `EmailField`.

## 5. Информационная безопасность (ISO 27001)

### Логирование (текущее состояние)

Используется стандартный Django `LogEntry` (`django.contrib.admin.models`).

- **Что записывается:** все действия через Django Admin — добавление, изменение, удаление объектов. Поля: `action_time`, `user`, `content_type`, `object_repr`, `action_flag`, `change_message`.
- **Доступ:** отображается в разделе **Activity Log** в панели администратора.
- **Защита:** `LogEntryAdmin` запрещает `add`, `change`, `delete` через Admin UI — записи доступны только для просмотра.
- **Ограничение:** логируются только действия через Admin. Прямые вызовы сервисов (`request_service.py`) и публичная форма (`/zetom/email/`) в `LogEntry` не попадают.

> Полноценная система логирования (Full Log / Partial Log / Incident Log по требованиям) — **не реализована**, запланирована.

### Целостность данных

- Soft delete через `django-safedelete` — данные не удаляются физически, уходят в архив.
- `approve_null_action` обёрнут в `@transaction.atomic` — при сбое любого шага (создание `RequestMain`, soft-delete `RequestNull`, отправка email) вся транзакция откатывается.

## 7. Инструкция для мануального тестирования

### Сценарий A: Полный цикл null → RequestMain

1. Открыть `GET /zetom/email/` — убедиться что форма отображается.
2. Заполнить форму: телефон `+48501600300`, NIP `7322215365`, email валидный.
3. Нажать отправить — **ожидаемый результат:** сообщение об успехе, запись появилась в `RequestNull` в Admin.
4. Открыть Admin → **Validation Window** → найти запись → открыть детальную страницу.
5. Нажать кнопку **Approve** — **ожидаемый результат:** редирект на `RequestMain`, `RequestNull` пропала из списка (soft-deleted).
6. Проверить Mailpit — должно быть 2 письма: при создании и при одобрении.

### Сценарий B: Переход к Oferta

1. Открыть Admin → **Information** → выбрать любой `RequestMain`.
2. Нажать кнопку **Oferta** — **ожидаемый результат:** редирект на `Oferta`, поле `price = 0`, поле `from_main` заполнено автоматически.
3. Вручную обновить `price` и сохранить.
4. Нажать **Oferta** повторно — **ожидаемый результат:** перебросит на уже существующую `Oferta`, дубликат не создастся.

### Сценарий C: Невалидные данные

1. Отправить форму с NIP `123` (не 10 цифр) — **ожидаемый результат:** форма не сохраняется, показывается ошибка валидации.
2. Отправить форму с телефоном `abc` — **ожидаемый результат:** аналогично.
