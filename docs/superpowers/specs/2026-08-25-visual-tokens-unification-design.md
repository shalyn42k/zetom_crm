## 2. Декомпозиция (контекст)

Общая задача «причесать интерфейс» разбита на три независимых проекта:

- **A — единый визуальный язык** (этот спек): токены, смерть серого, устранение дрейфа. Только цвет и его источник.
- **C — карточка заявки и список заявок**: правки по существу, кнопки, ссылки.
- **B — страницы документов** Oferta / Zlecenie / Wniosek: полная переделка плюс вложения файлов (сейчас шаблоны — заглушки на 23, 21 и 6 строк, а `RequestAttachment` умеет только `RequestNull` и `RequestMain`).

Порядок **A → C → B**. A первым, иначе C и B будут построены на сером и переделаны дважды.

**Входит:**

## 4. Архитектура токенов

### 4.1. Два слоя

`static/css/tokens.css`, подключается в [templates/unfold/layouts/skeleton.html](../../../templates/unfold/layouts/skeleton.html) **строкой выше** `custom_admin.css` — переменные должны существовать до первого потребителя.

**Слой 1 — сырая шкала.** Своего ничего: используются `--color-base-50…950` и `--color-primary-50…950`, которые Unfold уже отдаёт. Шкала фиксированная, по теме не меняется.

Имена проверены на работающем приложении, а не выведены из документации: в отрендеренном `/admin/` присутствуют все 22 переменные, `--color-base-900: oklch(21% .034 264.665)`. Тон 264 — холодный нейтральный; тон `primary` — 145, зелёный.

**Слой 2 — семантические роли.** Переключаются под `html.dark`:

| Роль | Светлая | Тёмная |
|---|---|---|
| `--surface` | `base-50` | `base-900` |
| `--surface-soft` | `base-100` | `base-800` |
| `--border` | `base-200` | `base-800` |
| `--border-strong` | `base-300` | `base-700` |
| `--text` | `base-900` | `base-100` |
| `--text-muted` | `base-600` | `base-300` |
| `--text-subtle` | `base-500` | `base-400` |
| `--input-bg` | `base-50` | `base-900` |
| `--input-border` | `base-300` | `base-700` |
| `--accent` | `primary-600` | `primary-400` |

Страницы просят роль, а не цвет. Смена `base` в `unfold_config` перекрашивает всё разом, включая хром.

**Тёмная тема ловится через `html.dark`**, не `data-theme="dark"` — Unfold ставит именно класс.

### 4.2. Статусные цвета

Unfold даёт только `base` и `primary`. Зелёный/красный/янтарный/синий/фиолетовый/slate для бейджей статусов останутся литералами — но **одним набором** в `tokens.css` вместо четырёх копий. Это и есть починка дрейфа §1.2: побеждают значения из трёх согласных файлов (`--purple: #7c3aed`, `--border: #e7e5e4`, лёгкая тень), `company_card` подтягивается к ним.

### 4.3. Смерть серого

`--custom-input-bg` перестаёт быть значением и становится алиасом `--input-bg` (в тёмной — `base-900`). Фиолетовый подтон уходит, поля сливаются с карточкой.

`--custom-input-focus-border` переводится на `--accent`, то есть на зелёный. **Это касается каждого поля ввода на сайте**, включая штатные формы Unfold. Решение принято сознательно: индиговый фокус был единственным местом, где появлялся цвет, отсутствующий в остальном интерфейсе.

### 4.4. Префиксные переменные остаются алиасами

Имена классов не трогаем, поэтому `--rm-card-bg`, `--up-card-bg`, `--vw-bg` и подобные **сохраняются**, но перестают быть значениями:

```
--rm-card-bg: var(--surface);
--up-card-bg: var(--surface);
--vw-bg:      var(--surface);
```

Правила, использующие эти переменные, не меняются вообще — меняется только источник цвета. Диффы остаются читаемыми, откат точечным.

Литералы, стоящие прямо в правилах, заменяются на `var(--…)`.

## 5. Фазировка

Каждый шаг самостоятельно отгружаем и проверяется скриншотами до/после.

1. **`tokens.css` + подключение.** Токены определены, никем не используются. Визуально ноль изменений — безопасная точка отката.
2. **`custom_admin.css`.** Умирает серый, зеленеет фокус. Маленький файл, мгновенный результат на всём сайте.
3. **`company_card.css` + `client_pages.css`.** Заодно устраняется дрейф.
4. **`validation_window.css`, `email_form.css`, `notification_badge.css`.** Мелочь.
5. **`requestmain_detail.css`.** Самый большой и рискованный — 175 точек. Отдельным шагом, с самой плотной проверкой.
6. **`userprofile_detail.css`.** Чужой модуль, **отдельным PR** (см. §7).

Порядок неслучаен: шаг 2 даёт результат, ради которого всё затевалось, вторым по счёту. Если после него работу остановить, проект останется в рабочем состоянии.

## 6. Проверка

### 6.1. Инвариант «нет литералов»

После миграции файла в нём не остаётся hex-литералов цвета:

```
grep -oE '#[0-9a-fA-F]{3,8}\b' <file>   →   пусто
```

Легальные исключения, перечисленные поимённо:

- `static/css/tokens.css` — единственное место, где литералы разрешены;
- `rgba(0,0,0,…)` в тенях — не hex, под инвариант не попадает;
- цвета внутри inline-SVG в шаблонах.

Инвариант даёт то, чего не даёт глаз: гарантию, что новый цвет не пролезет мимо токенов позже.

### 6.2. Скриншоты

Полный прогон по 9 экранам в двух темах — 18 снимков — делается дважды: базовый до работы и финальный после. Между шагами снимаются только затронутые страницы.

| # | Экран | Почему |
|---|---|---|
| 1 | Список заявок | одна из двух страниц, с которых началась задача |
| 2 | Карточка заявки | вторая; 175 литералов |
| 3 | Карточка персоны | эталон, измениться не должна |
| 4 | Карточка фирмы | дрейф `--purple` / `--border` / тень |
| 5 | Профиль юзера | эталон + чужой модуль |
| 6 | Inbox | эталон |
| 7 | Validation window | свой набор `vw-*` |
| 8 | Форма оферты | дефолтная форма Unfold, база для проекта B |
| 9 | Вход / 2FA | `skeleton.html` грузит токены и туда |

Снимки живут в рабочем каталоге сессии, в репозиторий не коммитятся.

### 6.3. Механика доступа

Админка за 2FA (`django_otp`), обычный логин браузером не проходится — TOTP-код у владельца. Порядок: сгенерировать служебную сессию на стороне Django (`force_login` + `DEVICE_ID_SESSION_KEY` активного устройства) и подставить cookie в браузер. Учётные записи не изменяются.

Без этого шага исполнитель упрётся в 2FA и начнёт городить обходы.

## 9. Открытые вопросы

- **Точное соответствие ролей ступеням шкалы** (§4.1) выбрано по здравому смыслу, не по замеру контраста. Если после первых скриншотов текст окажется блёклым или границы слишком контрастными, таблица правится — это ожидаемая итерация, а не дефект.
- **`email_form.css` содержит 34 переменные при 5 литералах** — он уже почти полностью токенизирован, но своим набором имён. Возможно, его достаточно переподключить к общим токенам без правки правил; решается при выполнении шага 4.
